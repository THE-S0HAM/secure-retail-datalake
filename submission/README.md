# Secure Retail Data Lakehouse

A complete, locally runnable Python data-engineering project that generates synthetic retail data, validates it, processes it through Raw/Bronze/Silver/Gold layers, applies privacy controls, loads Gold datasets into PostgreSQL when enabled, and produces audit-ready reports.

## Problem statement and objectives
Retail analytics needs realistic customer and transaction data without propagating unnecessary personal or payment details into analytical datasets. This project demonstrates how to:

- generate reproducible synthetic retail data at useful scale;
- enforce schema, quality, arithmetic, and reference-integrity rules;
- implement a medallion/lakehouse-style file pipeline;
- mask, redact, generalize, and tokenize sensitive fields;
- publish analysis-ready datasets and summaries;
- load verified Gold tables into PostgreSQL; and
- produce traceable run reports and automated tests.

## Architecture

```text
Synthetic generation
        |
        v
Raw CSVs -> source validation -> Bronze -> Silver -> Gold
                                                   |     |
                                                   v     v
                                             PostgreSQL Reports
```

Every run creates a unique `run_id`. Bronze adds lineage metadata. Validation and privacy gates stop the pipeline with a non-zero exit code before reports are published if a required check fails.

## Technology stack
Python 3.10+, pandas, Faker, SQLAlchemy, psycopg2, python-dotenv, PostgreSQL, HTML, and pytest. Package versions are pinned in `requirements.txt`.

## Verified dataset snapshot
The committed CSVs were generated by `submission/pipeline.py`; they are not placeholders or header-only samples.

| Layer | Customers | Products | Transactions | Other outputs |
|---|---:|---:|---:|---|
| Raw | 10,000 | 1,000 | 50,000 | — |
| Bronze | 10,000 | 1,000 | 50,000 | — |
| Silver | 10,000 | 1,000 | 50,000 | — |
| Gold | 10,000 | — | 50,000 | 9,934 customer summaries; 5 category summaries |

The generator uses fixed seeds for reproducible entities and reads `CUSTOMER_COUNT`, `PRODUCT_COUNT`, and `TRANSACTION_COUNT` from the environment.

## Data layers
**Raw:** Original synthetic customers, products, and transactions. Raw customer and payment fields exist only to demonstrate privacy transformation; all people and payment values are synthetic.

**Bronze:** Preserves source fields except CVV, which is removed immediately. Adds UTC `ingestion_timestamp` and `run_id` columns.

**Silver:** Replaces first and last names with `***`, masks email/phone/card values, removes street address and exact date of birth, derives `birth_year`, and adds deterministic salted SHA-256 `email_token` and `phone_token` values.

**Gold:** Removes direct names, masked email/phone/card fields, exact DOB, full address, and CVV. It generalizes postal codes, derives approximate age and age group, adds transaction-amount buckets and product category, and produces customer and category sales summaries.

## Privacy and validation
`validation.py` checks required columns, non-empty datasets, nulls, duplicate rows and keys, email/date formats, positive numeric values, transaction arithmetic, and customer/product references. Privacy checks inspect actual transformed frames and verify:

- CVV is absent from Bronze, Silver, and Gold;
- names, emails, phones, and cards are masked in Silver;
- address and exact DOB are absent from Silver;
- tokens are non-empty 64-character lowercase SHA-256 hex values;
- tokens deterministically match normalized Bronze source values using the private salt;
- raw email, phone, address, DOB, card number, and CVV are absent from Gold; and
- Gold postal codes, age groups, and amount buckets are populated.

`HASH_SALT` is required at runtime and must remain private. Changing it intentionally changes all deterministic tokens.

## PostgreSQL integration
A database-enabled run atomically replaces four tables: `customers_gold`, `transactions_gold`, `customer_summary`, and `sales_summary`. Credentials are URL-encoded, so reserved password characters such as `@`, `#`, `%`, `!`, `:`, and `/` are supported. The verified snapshot loaded 10,000, 50,000, 9,934, and 5 rows respectively.
Create the database before running, for example in `psql` as an administrator:

```sql
CREATE DATABASE secure_retail_lakehouse;
```

Copy `.env.example` to `.env` and set local values:

```env
DB_HOST=localhost
DB_PORT=5432
DB_NAME=secure_retail_lakehouse
DB_USER=postgres
DB_PASSWORD=your_local_password
HASH_SALT=generate_a_long_private_random_value
CUSTOMER_COUNT=10000
PRODUCT_COUNT=1000
TRANSACTION_COUNT=50000
DB_REQUIRED=true
```

`.env` is ignored and must never be committed. To exercise only the file pipeline when PostgreSQL is unavailable, set `DB_REQUIRED=false`; reports will explicitly show an empty database-load result.

## Installation
### Windows

```bat
python -m venv venv
venv\Scripts\activate
python -m pip install -r requirements.txt
copy .env.example .env
```

### Linux/macOS

```bash
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Edit `.env`, then run from this directory:

```bash
python pipeline.py
```

A successful run prints `Pipeline completed successfully` and a run ID. It regenerates all layer CSVs, validates data/privacy, optionally loads PostgreSQL, and refreshes all reports.

## Reports
- `validation_report.txt`: source-validation findings and privacy status.
- `data_quality_report.txt`: actual rows, missing values, and duplicate counts for Raw datasets.
- `pipeline_metrics_report.txt`: run ID, execution time, layer counts, PostgreSQL load counts, and statuses.
- `pipeline_summary.html`: browser-readable success summary with Gold and database counts.

Reports contain aggregate operational metadata only; they do not contain passwords, salts, CVV, card data, or raw PII.
## Tests and operational checks
Run the complete test suite:

```bash
python -m pytest -q
```

The tests cover generation, rejection of invalid values, masking, deterministic tokenization, Gold privacy/features, report secrecy, amount/postal buckets, special-character database URL handling, and an end-to-end file pipeline using temporary outputs.

With PostgreSQL configured and loaded, verify connectivity and all four tables:

```bash
python health_check.py
```

To create a local SQL backup, install PostgreSQL client tools (`pg_dump`) and run `python backup_database.py`. Backups are written under ignored `backups/` and are not part of this submission.

Equivalent count queries are:

```sql
SELECT COUNT(*) FROM customers_gold;
SELECT COUNT(*) FROM transactions_gold;
SELECT COUNT(*) FROM customer_summary;
SELECT COUNT(*) FROM sales_summary;
```

## Expected outputs
A successful default-size run produces 13 CSV files: three each in Raw, Bronze, and Silver, plus four in Gold. It also produces the four reports listed above and, when `DB_REQUIRED=true`, four PostgreSQL tables. Runtime logs, local environments, secrets, caches, and backups are intentionally excluded.
